pysanoid takes and prunes ZFS snapshots by policy. It is a Python port of link:{sanoid}[sanoid], the snapshot tool
written by Jim Salter and maintained with its contributors. It reads sanoid's configuration format, names snapshots
as sanoid does, and applies the same rules to decide what to take and what to destroy, except where
<<differences>> notes otherwise.

pysanoid has three design goals:

* *Compatibility with sanoid's files and names.* A valid `sanoid.conf` loads unchanged once it is copied to
  `/etc/pysanoid` (or found with `--configdir`). Snapshots are named `autosnap_YYYY-MM-DD_HH:MM:SS_<type>` in local
  time, exactly as sanoid names them, so a pool can move between pysanoid and Perl sanoid at any time.
* *No data loss from the configuration.* pysanoid matches sanoid's behaviour except where doing so has a plausible
  path to data loss, such as destroying a snapshot the configuration means to keep or failing to take one it asks
  for. A configuration that sanoid would load and then act on wrongly is refused with an error instead.
* *One file, few requirements.* pysanoid is a single file that needs Python 3.11 or later and nothing beyond the
  standard library. It should run on any UNIX-like system with OpenZFS and Python installed.

The terms this handbook uses, such as <<term-type,snapshot type>> and <<term-retention-count,retention count>>, are
described in <<terminology>>.

[preface]
== Why a Port

pysanoid runs on my TrueNAS appliance, where the appliance's own snapshot tools don't meet my needs:

* *The snapshot policy stays with the appliance.* A Periodic Snapshot Task's schedule, naming schema and lifetime
  are stored in the appliance's configuration database, not on the pool. Import the pool on another system, and
  nothing there knows how to keep its snapshots.
* *Existing sanoid snapshots don't fit its model.* A task keeps snapshots by age rather than by a count of each
  type, and manages only snapshots whose names match its naming schema. Configured to cover years of existing sanoid
  snapshots, the tasks pruned them unpredictably or not at all.
* *sanoid can't be installed.* sanoid is written in Perl and needs CPAN modules. The appliance doesn't support
  installing packages, and each update replaces the system files.

sanoid's model suits me and keeps a pool portable. The policy is a text file that can live on the pool, retention
is a count of each type, and everything needed to decide whether to keep a snapshot is on the pool itself: its type
in its name and its age in its `creation` property. pysanoid keeps that model in a single Python file with no
third-party dependencies.

=== A Pool That Moves

OpenZFS has a portable on-disk format, so a pool can move between operating systems with `zpool export` and
`zpool import`. The pool's `compatibility` property keeps it from enabling features that the other systems don't
support. My pool has moved from OmniOS to RHEL, then to Debian, and then to TrueNAS. pysanoid lets the snapshot
policy move with it.

=== Why No syncoid

pysanoid ports only sanoid itself. The other tools in the sanoid repository, such as syncoid, findoid and findbay,
are not ported. Because pysanoid's snapshot names are identical to sanoid's, syncoid replicates them as it would
sanoid's own. To replicate them with a TrueNAS Replication Task instead, add one naming schema per snapshot type in
use to the task's "Also include naming schema" field, for example `autosnap_%Y-%m-%d_%H:%M:%S_daily` and
`autosnap_%Y-%m-%d_%H:%M:%S_hourly`.

[[quick-start]]
== Quick Start Guide

This section installs pysanoid, previews a first run without changing any snapshots, and schedules it to run
hourly. The examples use a pool named `tank`, as the OpenZFS manual pages do.

=== Requirements

* *Python* 3.11 or later. Only the standard library is used.
* *Operating system:* a UNIX-like system with OpenZFS. pysanoid uses `flock(2)`, so it doesn't run on Windows.
  `zfs` must be on the `PATH`, and so must `zpool` if any dataset sets `prune_defer`.
* *Privileges:* run it as `root`, or as a user that can create and destroy snapshots (see `zfs allow`) and write to
  `/var/cache/pysanoid` and `/var/run/pysanoid`. Without a writable run directory, pysanoid still takes snapshots
  but prunes none.
* *Time zone:* the local zone is read from `/etc/localtime`, or from `$TZ` when it is set. Zone files under
  `/usr/share/zoneinfo` (or `$TZDIR`) are needed only when `$TZ` names a zone. If no zone can be read, pysanoid
  prints a warning and uses UTC.
* *Scheduler:* anything that can run it at least hourly. The repository includes systemd units.

=== Installing

pysanoid consists of one program and two configuration files. To install them, run these commands as `root` from a
copy of the repository:

[source,shell]
----
# install -m 755 pysanoid.py /usr/local/sbin/pysanoid.py
# mkdir -p /etc/pysanoid
# install -m 644 sanoid.defaults.conf /etc/pysanoid/
# install -m 644 sanoid.conf /etc/pysanoid/
----

`sanoid.defaults.conf` holds the default value of every setting; see <<sections-and-templates>> to override one.
`sanoid.conf` is the example configuration from the repository. Edit it to name your own datasets, as described in
<<configuration>>.

[WARNING]
====
Do not run pysanoid and Perl sanoid on the same datasets. Their snapshot names are identical, so each would count
and prune the other's snapshots, and neither can see the other's locks.
====

[[first-run]]
=== A First Run

The `--readonly` option reports what a run would take and destroy without taking or destroying anything (it may
still refresh pysanoid's cache files). Use it before the first real run and after every configuration change. This
configuration keeps seven daily snapshots of `tank/home`, of every dataset under it, and of `tank/backup`:

[source,ini]
----
[tank/home]
	use_template = home
	recursive = yes

[tank/backup]
	use_template = home
	prune_defer = 85

[template_home]
	hourly = 0
	daily = 7
	weekly = 0
	monthly = 0
	autosnap = yes
	autoprune = yes
----

Shortly after midnight UTC, with nine daily snapshots of each dataset already in place, a read-only run shows:

[source,shell]
----
# TZ=UTC pysanoid.py --cron --readonly --verbose
INFO: dataset cache expired - updating from zfs list.
INFO: cache expired - updating from zfs list.
INFO: taking snapshots...
taking snapshot tank/home@autosnap_2026-11-03_00:01:12_daily
taking snapshot tank/home/alice@autosnap_2026-11-03_00:01:12_daily
taking snapshot tank/backup@autosnap_2026-11-03_00:01:12_daily
INFO: pruning snapshots...
INFO: pruning tank/home@autosnap_2026-10-25_00:00:07_daily ...
INFO: pruning tank/home@autosnap_2026-10-26_00:00:07_daily ...
INFO: pruning tank/home/alice@autosnap_2026-10-25_00:00:07_daily ...
INFO: pruning tank/home/alice@autosnap_2026-10-26_00:00:07_daily ...
INFO: deferring snapshot pruning (tank/backup)...
----

The run would take a daily snapshot of each dataset, because the day's <<term-preferred-time,preferred time>> of
23:59 has passed since the last one was taken. `tank/home/alice` is included because `recursive = yes` applies
`tank/home`'s settings to every dataset under it. The run would also destroy the two oldest daily snapshots of
`tank/home` and `tank/home/alice`: each is more than seven days old, and at least seven newer ones remain.
`tank/backup` keeps all of its snapshots because its pool is no more than 85% full (see <<prune-defer>>).

A real `--cron` run decides what to prune from the snapshots that existed when it started, so it destroys exactly
what the read-only run reports. Under the systemd units below, pruning runs as a separate process after the take,
so it also counts the snapshot just taken and may destroy one more.

=== Running on a Schedule

The repository includes three systemd units, based on sanoid's Debian packaging:

* `pysanoid.service` takes the snapshots that are due. It pulls in `pysanoid-prune.service`, which runs after it
  finishes, whether or not the take succeeded.
* `pysanoid-prune.service` destroys snapshots that are past their retention.
* `pysanoid.timer` starts `pysanoid.service` every hour, with a random delay of up to two minutes.

NOTE: My configuration takes no `frequently` snapshots, so the timer runs hourly. pysanoid takes only the snapshots
that are due, so running it more often does no harm. If you take `frequently` snapshots, run pysanoid at least as
often as `frequent_period` (15 minutes by default), or some will be missed. sanoid's documentation suggests running
it every minute. To run every 15 minutes, change `OnCalendar=` in `pysanoid.timer`:

[source,ini]
----
[Timer]
OnCalendar=*:0/15
RandomizedDelaySec=60
----

Keep `RandomizedDelaySec=` well below the interval, and remove it for a timer that runs every minute.

To install the units and start the timer:

[source,shell]
----
# install -m 644 pysanoid.service pysanoid-prune.service pysanoid.timer /etc/systemd/system/
# systemctl daemon-reload
# systemctl enable --now pysanoid.timer
----

Both services name `pysanoid-alert@.service` as their `OnFailure=` handler, which is set up for my TrueNAS system
(see <<own-system-alert>>). On any other system, remove the `OnFailure=` line from both services or point it at a
handler of your own.

Both services also set `TZ=UTC`, as sanoid's Debian units do, so snapshots are named in UTC and preferred times
such as `daily_hour` are read in UTC. To use local time instead, remove `Environment=TZ=UTC` from both services or
set `TZ` to your zone. Use the same zone for manual runs, as in the example above.

=== Watching It

These commands show when the timer last ran and when it runs next, what each run did, and which snapshots exist:

[source,shell]
----
# systemctl list-timers pysanoid.timer
# journalctl -u pysanoid.service -u pysanoid-prune.service
# zfs list -t snapshot -r tank
----

See link:{systemd-man}/systemd.timer.html[systemd.timer(5)] and link:{openzfs-man}/8/zfs-list.8.html[zfs-list(8)]
for their other options.

[[configuration]]
== Configuration

pysanoid reads `sanoid.conf` and `sanoid.defaults.conf` from `/etc/pysanoid`, or from the directory named by
`--configdir`, so it never reads or changes Perl sanoid's files in `/etc/sanoid`. Both files use sanoid's format,
and a valid sanoid configuration copied from `/etc/sanoid` loads unchanged.

=== Sections and Templates

A section is named after a dataset, with no leading slash, and holds the settings for that dataset:

[source,ini]
----
[tank/home]
	use_template = home
----

A section named `template_<name>` holds settings that other sections share, and a section applies it with
`use_template = <name>`. A section's own settings override its templates' settings, which override the defaults.
Templates are conventionally placed below the sections that use them.

To change a default for every section, add a `[template_default]` section to `sanoid.conf`, as the header of
`sanoid.defaults.conf` describes. Leave `sanoid.defaults.conf` unedited: it also defines which settings pysanoid
accepts (any other key is an error), and installing a newer copy discards local edits.

[NOTE]
====
A setting a template omits comes from `sanoid.defaults.conf`, which keeps 48 hourly, 90 daily and 6 monthly
snapshots. A template that should keep none of a type must say so explicitly, for example `hourly = 0`.
====

[[retention]]
=== Retention Counts

Each <<term-type,snapshot type>> has a <<term-retention-count,retention count>>: `frequently`, `hourly`, `daily`,
`weekly`, `monthly` and `yearly`. pysanoid keeps at least that many snapshots of the type, and destroys an older
one only when it is older than the count multiplied by the type's period. The periods are `frequent_period`
minutes, one hour, one day, seven days, 31 days and 365.25 days. With `daily = 7`, pysanoid destroys a daily
snapshot once it is more than seven days old and at least seven newer daily snapshots exist.

A count of `0` takes no snapshots of that type and destroys any that exist. To keep twelve hourly and seven daily
snapshots of `tank/media`, add:

[source,ini]
----
[tank/media]
	hourly = 12
	daily = 7
	weekly = 0
	monthly = 0
	yearly = 0
----

A blank, negative or malformed count (such as `3o` or `1_0`) stops the prune run before its first destroy, where
sanoid would read it as 0 or as a different number. Taking reads such a count as sanoid does and reports it.

[[preferred-times]]
=== Preferred Times

Each type is taken by the first run after its <<term-preferred-time,preferred time>>. These defaults apply unless a
section or template overrides them:

[cols="1,2,1"]
|===
| Type | Settings | Default

| hourly
| `hourly_min`
| minute 0 of each hour

| daily
| `daily_hour`, `daily_min`
| 23:59

| weekly
| `weekly_wday`, `weekly_hour`, `weekly_min`
| Monday, 23:30

| monthly
| `monthly_mday`, `monthly_hour`, `monthly_min`
| the 1st, 00:00

| yearly
| `yearly_mon`, `yearly_mday`, `yearly_hour`, `yearly_min`
| 1 January, 00:00
|===

Frequent snapshots are taken at each multiple of `frequent_period` minutes past the hour (15 by default: :00, :15,
:30 and :45). Preferred times are read in the local time zone, which the systemd units set to UTC.

pysanoid computes preferred times from the time zone database, so a daylight-saving change neither skips a
snapshot nor takes one twice.

[[recursion]]
=== Recursion

A section's settings normally apply only to its own dataset. `recursive` extends them to the datasets below it:

`recursive = yes`:: Every dataset under the section inherits its settings and is snapshotted separately. A
descendant with its own section starts from the parent's settings, and its own settings override them. Its section
must come after the parent's.
`recursive = zfs`:: The whole tree is snapshotted atomically with one `zfs snapshot -r` and managed entirely by the
section's settings. A section that also takes or prunes a dataset inside the tree is refused.

`process_children_only = yes` skips the section's own dataset and manages only the datasets below it.
`skip_children = yes` excludes the datasets below the section.

[IMPORTANT]
====
Place a dataset's own section below the recursive section above it. sanoid reads sections in order, and a section
placed above is replaced by its parent's settings, which can destroy snapshots the child section means to keep.
pysanoid refuses such a configuration and names both sections.
====

See link:{openzfs-man}/8/zfs-snapshot.8.html[zfs-snapshot(8)] for how `-r` takes a recursive snapshot.

[[prune-defer]]
=== Deferring Pruning

`prune_defer` holds back pruning of a dataset's snapshots until the pool's used capacity exceeds the given
percentage. This suits a dataset whose snapshots should be kept for as long as the pool has room:

[source,ini]
----
[tank/backup]
	use_template = home
	prune_defer = 85
----

While `tank` is 85% full or less, a run reports `deferring snapshot pruning (tank/backup)...` and destroys none of
`tank/backup`'s snapshots. Once usage exceeds 85%, they are pruned by their counts as usual. pysanoid reads the pool's capacity with `zpool list`; see link:{openzfs-man}/8/zpool-list.8.html[zpool-list(8)].

[[hooks]]
=== Script Hooks

A section can run a command before and after its snapshots are taken, and before and after each snapshot is
destroyed. Each command runs as Perl's `system()` would run it: through `/bin/sh` if it contains a shell
metacharacter, otherwise directly, with its words as arguments. A hook still running after `script_timeout`
seconds (5 by default) is killed and counts as failed; processes it started are not killed.

[cols="2,3,4"]
|===
| Setting | When it runs | Variables it gets

| `pre_snapshot_script`
| before a dataset's snapshots
| `SANOID_SCRIPT=pre`, `SANOID_TARGET`, `SANOID_TARGETS`, `SANOID_TYPES`, `SANOID_SNAPNAME`, `SANOID_SNAPNAMES`

| `post_snapshot_script`
| after them; if the pre hook failed, only when `force_post_snapshot_script` is set
| the same, with `SANOID_SCRIPT=post` and `SANOID_PRE_FAILURE` (1 or 0)

| `pre_pruning_script`
| before each destroy; a non-zero exit keeps that snapshot
| `SANOID_TARGET`, `SANOID_SNAPNAME`

| `pruning_script`
| after each destroy
| `SANOID_TARGET`, `SANOID_SNAPNAME`, `SANOID_SCRIPT=prune`
|===

`SANOID_TYPES` and `SANOID_SNAPNAMES` are comma-separated. As in sanoid, `SANOID_SNAPNAME` is the bare snapshot
name for the pre hook and `dataset@name` for the post hook. With `no_inconsistent_snapshot = yes`, a failed
`pre_snapshot_script` skips that dataset's snapshots for the run.

[[config-errors]]
=== Configuration Errors

pysanoid refuses a mistake that sanoid would accept and then act on wrongly, naming the setting and the section.
Most are caught when the configuration loads, before anything is taken or destroyed. A malformed retention count or
`prune_defer` is caught before the first destroy. For example, a typo made while turning pruning off leaves pruning
on in sanoid; pysanoid refuses it:

[source,shell]
----
# pysanoid.py --prune-snapshots --readonly
FATAL: 'autoprune' in [tank/home] must be one of 0, 1, FALSE, False, NO, No, OFF, ON, Off, On, TRUE, True, YES, Yes, false, no, off, on, true, yes, got 'noo'.
----

A template that does not exist is refused the same way:

[source,shell]
----
# pysanoid.py --cron --readonly
FATAL: [tank/home] in /etc/pysanoid/sanoid.conf uses template 'hom', but there's no [template_hom] section defined.
----

Both runs exit with status 1, and nothing is taken or destroyed. pysanoid also refuses two sections that take or
prune the same dataset.

[[running]]
== Running pysanoid

=== Options

[cols="1,3"]
|===
| Option | What it does

| `--take-snapshots` | take the snapshots that are due
| `--prune-snapshots` | destroy the snapshots past their retention
| `--cron` | take, then prune; this is also the default, run verbosely, when no options other than the directory options are given
| `--readonly` | report what would be taken and destroyed without taking or destroying anything
| `--verbose` | report each step
| `--quiet` | with `--cron`, turn off `--verbose`
| `--debug` | print the merged configuration and a snapshot summary for each dataset; with an action, also run it verbosely
| `--force-update` | refresh the dataset and snapshot caches from zfs, ignoring their age
| `--cache-ttl=SECONDS` | how long the dataset and snapshot caches stay valid (default 1200)
| `--configdir=DIR` | the configuration directory (default `/etc/pysanoid`)
| `--cache-dir=DIR` | the cache directory (default `/var/cache/pysanoid`)
| `--run-dir=DIR` | the lock file directory (default `/var/run/pysanoid`)
| `--force-prune` | accepted and ignored with a warning, as in sanoid
| `--version` | print pysanoid's version
| `--help` | print a usage summary
|===

To see how pysanoid has merged the configuration's sections, templates and defaults, run:

[source,shell]
----
# pysanoid.py --debug
----

pysanoid first lists each value that a template or section overrides, then prints every dataset's settings as
pysanoid will apply them, followed by a summary of each dataset's snapshots.

=== Exit Status

pysanoid exits 0 when the run completes as configured, and 1 otherwise:

* A configuration error stops the run before anything is taken or destroyed. A malformed retention count or
  `prune_defer` stops it before the first destroy.
* A failure that doesn't stop the run, such as a snapshot that couldn't be taken or a cache that couldn't be
  written, is reported, and the run exits 1 when it finishes.

A command-line usage error exits 2. Errors are written to standard error, and a non-zero exit status makes the
systemd unit show as failed.

[[own-system]]
== Where I run pysanoid

My system has run pysanoid since August 2026. It is a TrueNAS appliance, so pysanoid has to live on a pool, mail its
failures through the system's own mail settings, and coexist with the snapshot tasks in the TrueNAS web interface.

=== Keeping pysanoid on a Pool

An appliance update replaces the system files, including anything installed alongside them, such as the systemd
units and timer. Keep `pysanoid.py`, `pysanoid_alert.py`, `sanoid.conf` and `sanoid.defaults.conf` together in a
directory on a pool, where they survive updates and move with the pool (see <<a-pool-that-moves>>).
`pysanoid_alert.py` imports `pysanoid.py`, so the two must stay in the same directory.

Then edit the three services to use that directory. In `pysanoid.service`, and likewise in `pysanoid-prune.service`
with `--prune-snapshots`:

[source,ini]
----
ConditionFileNotEmpty=/mnt/tank/bin/pysanoid/sanoid.conf
ExecStart=/mnt/tank/bin/pysanoid/pysanoid.py --configdir=/mnt/tank/bin/pysanoid --take-snapshots --verbose
----

In `pysanoid-alert@.service`:

[source,ini]
----
ExecStart=/mnt/tank/bin/pysanoid/pysanoid_alert.py failure %i
----

Reinstall the units after each update. Alternatively, run pysanoid from a Cron Job in the web interface, for
example `TZ=UTC /mnt/tank/bin/pysanoid/pysanoid.py --configdir=/mnt/tank/bin/pysanoid --cron`. Set `TZ` to match
the units, so snapshot names and preferred times use the same zone however pysanoid is started.

[[own-system-alert]]
=== Mail on Failure

`pysanoid-alert@.service` runs `pysanoid_alert.py failure`, which mails the failed run's log to the system's local
administrators through TrueNAS's own mail settings, so no address or password is stored with it.

`pysanoid_alert.py` can also check that every snapshot type pysanoid is configured to take has a recent snapshot.
This catches failures that a unit can't report, such as units removed by an update or a timer that stopped firing.
Run it as `root` from a Cron Job, with *Hide Standard Output* checked and *Hide Standard Error* unchecked:

[source,shell]
----
/mnt/tank/bin/pysanoid/pysanoid_alert.py freshness --configdir=/mnt/tank/bin/pysanoid
----

Mail is sent with TrueNAS's `midclt`, so sending works only on TrueNAS. With `--no-mail`, either command prints the
message instead of sending it.

=== The System's Own Snapshot Tasks

A Periodic Snapshot Task prunes every snapshot, on the datasets it covers, whose name matches its naming schema.

[WARNING]
====
Do not enable a Periodic Snapshot Task whose naming schema could match `autosnap_` names on a dataset that pysanoid
manages. The task would prune pysanoid's snapshots by its own lifetime. Use one snapshot method per dataset, not
both.
====

To replicate pysanoid's snapshots with a Replication Task, see <<why-no-syncoid>>.

[[differences]]
== Differences from sanoid

pysanoid follows sanoid at commit link:{sanoid-pin}[`d39b51a`] on sanoid's `master` branch, dated 5 June 2026. The
script at that commit still reports version 2.3.0, but it postdates the 2.3.0 release and includes the fixes merged
since. pysanoid matches sanoid's behaviour except where doing so has a plausible path to data loss. When moving from
sanoid, expect these differences:

* *Separate directories.* pysanoid uses `/etc/pysanoid`, `/var/cache/pysanoid` and `/var/run/pysanoid`, and never
  reads or changes sanoid's. Copy `sanoid.conf` and `sanoid.defaults.conf` from `/etc/sanoid` to begin.
* *Stricter configuration checks.* A configuration that sanoid would load and then act on wrongly is refused. This
  includes a template that doesn't exist, a typo in an on/off setting, a child section placed above its recursive
  parent, and two sections that take or prune the same dataset. See <<config-errors>>.
* *Malformed retention counts stop pruning.* A blank, negative or malformed count stops the prune run before
  anything is destroyed, where sanoid would prune by 0 or by a different number.
* *Failures exit non-zero.* A snapshot that could not be taken makes the run exit 1, so the failure shows in
  systemd.
* *Hook timeouts are contained.* A hook that outlives `script_timeout` is killed and the run carries on, where
  sanoid itself is killed mid-run.
* *No Nagios checks.* The `--monitor-snapshots`, `--monitor-health` and `--monitor-capacity` options are not
  implemented. syncoid, findoid and findbay are separate programs; see <<why-no-syncoid>>.

pysanoid also handles clock errors and daylight-saving changes more safely than sanoid. link:DEVIATIONS.md[DEVIATIONS.md]
lists every difference, and every place where matching sanoid needed explanation, with the reason and the evidence.

[[audit]]
== The Audit

pysanoid was audited six times between 21 September and 25 October 2026, and sanoid's newest reports were reviewed
on 28 October. Five of the audits ran sanoid's own Perl, at the pinned commit, beside pysanoid on the same input,
rather than relying on reading the code. The fourth audit focused on security and data safety.
link:AUDIT.md[AUDIT.md] records what each audit checked, found and fixed.

=== Bugs in the Port

In some places the port had drifted from sanoid by accident. Each was fixed to match sanoid, with a test that fails
before the fix and passes after it. Among them:

* A malformed or negative `script_timeout` could crash the take run, leaving other datasets without snapshots, or
  crash the prune run after it had already destroyed snapshots. This was the most safety-critical bug found.
* When the snapshot cache was missing, adding to it built a new cache that held only the new snapshots. Every other
  type then looked overdue and was taken again, and the extra snapshots used up retention.
* How a recursive section and a template were merged depended on the order of the sections, so a child's own
  `process_children_only` or `recursive = zfs` could be lost.
* A blank `prune_defer` turned off the pool capacity check instead of failing.
* The dataset cache was loaded lazily, where sanoid loads it eagerly, so it was rewritten on every run on my
  system. This cost only extra I/O and a misleading log line, but it was the most widespread bug found.

=== Bugs in sanoid

Elsewhere, sanoid itself can destroy snapshots the configuration means to keep, or silently stop taking snapshots.
pysanoid deviates from sanoid in those places; see <<differences>>.

=== What sanoid's Users Reported

One audit read all 1,061 issues and pull requests in sanoid's repository as of 26 September 2026, and checked those
about the code pysanoid ports against it. Most of the bugs users reported were already handled by pysanoid. The one
it still shared, #1021, was fixed in 0.1.37, and the review of 28 October took up two newer reports, #1116 and #1119.
Some of these bugs have since been fixed in sanoid, and some remain open:

[cols="2,4"]
|===
| sanoid reports | What pysanoid does

| {sanoid}/issues/1021[#1021]
| A dataset's section placed above the recursive section it belongs under is refused. In sanoid, it is silently
replaced by the parent's settings.

| {sanoid}/issues/702[#702], {sanoid}/issues/938[#938], {sanoid}/issues/1038[#1038], {sanoid}/pull/1039[#1039]
| A `use_template` that names no template is an error, not a run on the defaults.

| {sanoid}/issues/834[#834], {sanoid}/issues/901[#901], {sanoid}/issues/952[#952]
| Every value is trimmed, and a repeated key reads as its first value. sanoid has fixed this for the cases these
users met. pysanoid covers the places it did not reach.

| {sanoid}/issues/671[#671], {sanoid}/issues/394[#394], {sanoid}/issues/440[#440]
| A snapshot that could not be taken makes the run exit non-zero, and a bad value costs only its own type.

| {sanoid}/issues/1030[#1030], {sanoid}/issues/1116[#1116]
| A hook that outlives `script_timeout` is killed, and the run carries on.

| {sanoid}/issues/1063[#1063], {sanoid}/issues/790[#790], {sanoid}/issues/391[#391], {sanoid}/issues/534[#534]
| Runs lock with flock(2), and a cache that cannot be written never stops a run.

| {sanoid}/issues/155[#155], {sanoid}/issues/395[#395], {sanoid}/issues/406[#406], {sanoid}/issues/409[#409]
| Preferred times come from the system's time zone database, so changes to and from summer time are handled.

| {sanoid}/issues/1119[#1119]
| A snapshot dated more than five minutes ahead of the clock is set aside, so it neither stops snapshots of its type
nor takes the place of one the retention keeps.
|===

Because the commit pysanoid follows postdates sanoid's 2.3.0 release (see <<differences>>), bugs in 2.3.0 that were
fixed before that commit, such as the duplicate snapshots under `recursive = zfs` fixed by {sanoid}/pull/1023[#1023],
do not affect pysanoid. AUDIT.md's section "What upstream's users reported" covers the reports behind each
difference, along with lessons for running pysanoid.

[[testing]]
== Testing pysanoid

pysanoid is tested in two ways:

* `test_pysanoid.py` and `test_pysanoid_alert.py` are pytest suites. To run them as an ordinary user:
+
[source,shell]
----
% python3 -m pytest test_pysanoid.py test_pysanoid_alert.py
----
* `dev/` compares pysanoid with sanoid's own Perl on the same input: whole runs, each part of a run, and thousands
  of generated cases. It needs Perl with Capture::Tiny, plus two CPAN modules that `dev/fetch_cpan.py` fetches. See
  link:dev/README.md[dev/README.md].

The tests and the comparison with sanoid run on macOS under Python 3.11. GitHub Actions runs the tests and ruff on
Linux under Python 3.11 for every push to `main` and every pull request. pysanoid is written to run on FreeBSD and
other Linux distributions, but has not yet been run on a real pool there.

[[terminology]]
== Terminology

[[term-snapshot]]snapshot::
A read-only copy of a dataset at one instant. See link:{openzfs-man}/8/zfs-snapshot.8.html[zfs-snapshot(8)].

[[term-type]]snapshot type::
One of `frequently`, `hourly`, `daily`, `weekly`, `monthly` and `yearly`. A snapshot's type is the last part of its
name: `autosnap_2026-11-03_00:01:12_daily` is a daily.

[[term-retention-count]]retention count::
The number of snapshots of a type that a dataset keeps, such as `daily = 7`. See <<retention>>.

[[term-preferred-time]]preferred time::
The time at which a type is due, such as minute 0 of each hour for an hourly or 23:59 for a daily. A type is taken
by the first run after it. See <<preferred-times>>.

[[term-section]]section::
The part of `sanoid.conf` that names a dataset, such as `[tank/home]`, and holds its settings.

[[term-template]]template::
A section named `template_<name>`, whose settings other sections share through `use_template`. See
<<sections-and-templates>>.

[[term-recursion]]recursion::
Extending a section's settings to the datasets below it, with `recursive = yes` or `recursive = zfs`. See
<<recursion>>.

[[term-prune-defer]]prune_defer::
A pool capacity, as a percentage, at or below which a dataset's snapshots are not pruned. See <<prune-defer>>.

[[term-hook]]hook::
A command a section runs around taking or destroying its snapshots. See <<hooks>>.

[[term-autosnap]]autosnap_ name::
The name pysanoid and sanoid give every snapshot they take: `autosnap_`, the date and time, and the type. If that
name is already taken, as it can be in the hour repeated when daylight-saving time ends, the snapshot is taken again
with `dst` before the type, such as `autosnap_2026-10-25_01:00:00dst_hourly`.

[[term-cache]]snapshot cache::
A list of the pool's snapshots that pysanoid keeps in `/var/cache/pysanoid`, so that most runs need not list every
snapshot from zfs. `--force-update` refreshes it from zfs, and `--cache-ttl` sets how long it stays valid.
